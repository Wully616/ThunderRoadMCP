# Local bridge protocol

The in-game mod listens only on `127.0.0.1` (default TCP port `47831`). Each connection carries one UTF-8 JSON Lines request (one JSON object followed by newline); the server returns one response and closes the connection. Request and response lines are limited to 64 KiB. Oversized results return a small error response rather than truncated JSON.

## Local bridge configuration

The bridge config path is `%LOCALAPPDATA%\ThunderRoadMcp\bridge.json` by default. `THUNDERROAD_MCP_CONFIG` overrides that path; the MCP host and game process must use the same path. The bridge stays disabled unless this file exists, parses, and sets `enabled` to `true`. Installing the mod alone does not open a listener. Keep this file out of source control.

Generate a fresh 32-byte cryptographically random secret and encode it as 64 hexadecimal characters. Do not use a password or reuse another credential. Use the Windows PowerShell 5.1-compatible recipe in the [bridge configuration](usage.md#bridge-configuration) section of the usage guide, which creates the file without overwriting an existing config.

```json
{
  "enabled": true,
  "host": "127.0.0.1",
  "port": 47831,
  "token": "<64 hex characters>"
}
```

The separate host launch config is `%LOCALAPPDATA%\ThunderRoadMcp\launch.json` with `{ "executablePath": "<absolute path>", "arguments": ["<argument>"] }`. `THUNDERROAD_MCP_LAUNCH_CONFIG` can override the config path. Arguments are passed as an array, never through a shell; for a cold start with no requested level use `["-level", "Home"]`, or pass a user-requested target directly as `["-level", "<target>"]`. The bridge initializes only after the main-menu/Home startup; wait with `game_wait_ready` or check `game_status` before bridge-backed calls. `game_load_level` requires a ready bridge and is not a way to complete initial startup. The host stops/restarts only processes it launched itself, and does not stop one on host exit. Never pass the bridge token through command-line arguments or check in either local config.

`game_install_mod` accepts `{ "packagePath": "<absolute path to ThunderRoadMcp.zip>" }`. It derives `<game executable directory>/<executable stem>_Data/StreamingAssets/Mods/ThunderRoadMcp` from `launch.json`, accepts only the root bridge DLL, a `manifest.json` naming `ThunderRoadMcp`, and `runtime/*.dll.payload` files, rejects duplicate/unexpected/traversal paths and content over 256 MiB, stages extraction, then moves the completed directory into place. It refuses any existing destination and does not launch or reload the game; restart manually after installation.

The host executable also supports `--list-installations` (the same JSON envelope as `game_installations`) and `--install-bridge <absolute-zip> --game-executable <absolute-exe>`. These CLI modes run before MCP startup, reuse the same discovery and staged package validation, do not write either config or launch the game, and emit only JSON on stdout. Run `--help` for usage.

## Wire messages

Request:

```json
{"id":"request-1","token":"<secret>","method":"status","diagnostics":false,"parameters":{}}
```

Success response:

```json
{"id":"request-1","success":true,"result":{},"timings":{"bridgeRequestTotalMs":0.42}}
```

Failure response: `{"id":"request-1","success":false,"error":"message","timings":{"bridgeRequestTotalMs":0.42}}`. Authenticated requests accepted for dispatch include top-level `timings` on success or failure; malformed requests and authentication failures do not. Unknown methods and invalid parameters fail without executing game code. Every accepted request gets one response before its connection closes.

## Timing metadata

Bridge timing is opt-in. The bridge request's optional `diagnostics` boolean defaults to `false`; the host sets it from `THUNDERROAD_MCP_DIAGNOSTICS=1`, and direct authenticated bridge clients may set it to `true`. Setting `THUNDERROAD_MCP_DIAGNOSTICS=1` in the game process also opts in. With diagnostics disabled, bridge responses omit the `timings` field and normal MCP responses contain no detailed timing block. When enabled, the bridge reports bounded top-level durations separately from `result`: `bridgeRequestTotalMs` covers dispatch; `compilerQueueWaitMs` waits for the compiler slot; `compilationMs` covers compilation; `referenceInitializationMs`, `parseMs`, `emitMs`, and `assemblyLoadMs` separate evaluator reference, parse, emit, and load work; `mainThreadQueueWaitMs` measures queue-to-start delay; `invocationMs` measures snippet execution; and `serializationMs` measures result JSON serialization. Unstarted/unavailable stages are omitted, not reported as zero. This is server timing, not end-to-end client latency.

When host diagnostics are enabled with `THUNDERROAD_MCP_DIAGNOSTICS=1`, the host copies available bridge timings into MCP `_meta.timings`, adds `hostTotalMs`, and adds `bridgeRoundTripMs`; clients that hide `_meta` may receive the concise opt-in timing text block after the domain result. With diagnostics disabled these details are absent. Measurements are server-side, not client-observed MCP latency.


## Methods and result shapes

- `status`, parameters `{}` by default or `{"includeAssemblies":true}` to opt in: always returns `{ "bridgeReady": true, "processId": 1, "productName": "...", "gameVersion": "...", "unityVersion": "...", "currentLevel": "..."|null, "levelState": "...", "sceneReady": true }`. With `includeAssemblies:true`, it also returns `loadedAssemblies` (file-backed assemblies with MVIDs, capped at 128 entries), `loadedAssemblyCount` (full eligible count), and `loadedAssembliesTruncated`. With the default false value, the bridge does not enumerate or sort assemblies and omits all inventory fields. Host `game_status` strips `loadedAssemblies` from nested status when false to remain compact with older bridges, while retaining other raw fields. `game_wait_ready` always uses compact status.
- `logs`, parameters `{ "since": 0 }`: `{ "entries": [{ "sequence": 1, "timestamp": "...", "level": "...", "message": "...", "stackTrace": "..." }], "nextSequence": 1 }`. The ring retains 512 entries; each response returns at most 3 entries. When `since` is `0` or omitted, the newest up to 3 entries are returned and `nextSequence` is the current newest sequence. When `since` is positive, entries after that sequence are returned and `nextSequence` is the last returned sequence, or the current newest sequence when fewer than 3 entries were returned. Each message/stack trace is capped at 512/2048 characters and carries an explicit `…[truncated]` marker when clipped.
- `runtime`, parameters `{ "action": "list" }`, `{ "action": "inspect", "key": "..." }`, `{ "action": "stop", "key": "..." }`, or `{ "action": "clear" }`: all state access and DTO construction run on Unity's main thread. `list` returns at most 128 coroutines and 128 named values, with 128-character type names and 32-character string/name previews; it reports omitted entries while retaining total counts. `inspect` requires a non-empty key of at most 128 characters and returns `{ "action": "inspect", "key": "...", "found": true|false, "type": "..."|null, "typeTruncated": false, "value": ...|null }`; missing keys (`found:false`) differ from stored null (`found:true`, `value.kind:"null"`). It supports strings, booleans, numeric primitives, enums, Vector2/3/4, Quaternion, Color, and exact one-dimensional arrays or exact `List<T>` collections whose element type is one of those supported scalar/value shapes. Collections return at most 16 elements and disclose their full count/truncation. Strings and type names are bounded to 256 characters for inspect. Integer values above JavaScript's exact-integer range and decimal values use a decimal string with `representation:"decimalString"`; NaN and positive/negative infinity use `"NaN"`, `"+Infinity"`, or `"-Infinity"` with `representation:"string"`. Unity value-type non-finite components are also encoded as strings. Unity objects return bounded name/instanceId and `destroyed`; arbitrary objects are opaque. The bridge never serializes arbitrary stored objects, invokes user property getters/ToString overrides, or enumerates user collections. Inspect results include the bridge envelope and UTF-8 escaping within the 64 KiB response limit. `stop` requires a non-empty key and returns `{ "action": "stop", "key": "...", "stopped": true|false }`; `clear` stops all managed coroutines and clears named references but does not unsubscribe events or destroy objects.

- `load_level`, parameters `{ "levelId": "...", "mode": "..." }`: validates both as non-empty strings of at most 256 characters and calls `LevelManager.LoadLevel(levelId, mode)` on the Unity main thread. Returns `{ "levelId": "...", "mode": "...", "currentLevelBefore": "..."|null, "levelStateBefore": "...", "sceneReadyBefore": true|false }`. The returned fields describe the state immediately before the request. Loading is asynchronous; `currentLevelBefore` can still name the previous level while the load is in progress. The MCP host's optional `game_load_level(waitUntilReady:true)` waits separately for status polling; it does not change this bridge method's response. Exceptions from the game surface as bridge errors.
- `spawn_item`, parameters `{ "itemId": "...", "x": 0, "y": 0, "z": 0, "key": "...", "disallowDespawn": true }`: resolves `Catalog.GetData<ItemData>(itemId)` and starts `ItemData.SpawnAsync` through a bridge-managed coroutine on the Unity main thread. `x`, `y`, and `z` are optional, but must be supplied together, must be finite, and must be within ±1000000; when omitted the item spawns at the player's head plus 1.5 m forward. `key` is optional and defaults to a generated `item-<12 hex>` value. `disallowDespawn` defaults to true and sets `Item.DisallowDespawn`. The network handler waits up to 12 seconds (the coroutine itself gives the spawn callback 8 seconds) without blocking the main thread. Returns `{ "key": "...", "itemId": "...", "position": { "x": 0, "y": 0, "z": 0 }, "instanceId": 0, "name": "..." }` with the actual world position, Unity instance ID, and object name. An unknown or empty catalog id is an error; a partial coordinate triple, a key longer than 128 characters, or a spawn timeout is an error.
- `evaluate`, parameters `{ "code": "...", "timeoutMs": 10000 }`: compiles a C# statement body into a method returning `object`, invokes it synchronously on Unity's main thread, and returns its JSON-safe result. The generated source imports `ThunderRoadMcp.Bridge`, so snippets can use `McpRuntime.Current` directly. Compilation runs off-thread and its references are cached from loaded process assemblies plus the installed game's `Managed` directory; dynamic/evaluation assemblies without a file location are excluded. `timeoutMs` covers compilation, compiler-queue wait, and dispatch, bounded to 1–30000 ms. Expired queued work is skipped. A running C# method or serialization cannot be forcibly interrupted. Compiler diagnostics and full runtime exception details are errors, bounded to 4 KiB; snippet diagnostics refer to `evaluation.cs` line numbers. Top-level `await`, returned `Task` values, and frame-aware evaluation are unsupported; a returned `Task` is rejected before serialization rather than blocked on. Compiled evaluation assemblies remain loaded until the game process restarts. Evaluation does not patch methods or preserve/reload mod state.

The result object is serialized on Unity's main thread, before it is detached from game objects and sent over TCP. No Unity API calls are made by the network/compiler workers. The bridge caps clients and queued work; stopping/unloading closes the listener and active sockets and cancels pending work. Client EOF also cancels the request lifetime: queued main-thread work is skipped and uncommitted spawns are rolled back. A synchronous C# evaluation already running cannot be preempted. The protocol has no frame-aware/asynchronous evaluation guarantee.

Evaluation failures retain the readable `error` string and may add `errorCode`, `executionOutcome`, and structured `diagnostics`. Outcomes are `not_started` for known pre-invocation failures, `completed_result_unavailable` when invocation returned but its result could not be serialized or fit the response envelope, and `unknown` when execution may have begun or the peer does not provide outcome metadata. Clients must not automatically retry an `unknown` evaluation. Roslyn diagnostics include the compiler ID, severity, message, and submitted-source line, column, and span; structured diagnostics are limited to 20 entries and 256 message characters per entry to keep error responses bounded.

The serialized evaluation result subtree is limited to 62 nested JSON objects/arrays. Depths 60–62 are sent normally; 63 or greater becomes a small structured `evaluation.result_depth_exceeded` failure before the host parses the reply. The 64-KiB UTF-8 line and newline guard still applies to both successful results and failure envelopes.

The process-local Roslyn reference cache is keyed by the full bridge DLL path, not by hashes/MVIDs for every reference. It includes the game's `Managed` DLLs and file-backed loaded process assemblies when first initialized, and does not refresh after same-path file replacement or a later assembly load. A replacement DLL is not hot-loaded into Unity; restart the game to use changed references/code. `referenceInitializationMs` is opt-in cache access/initialization timing; no live timing was collected here to justify automatic invalidation.

Legacy helper semantics remain: `McpRuntime.Get<T>`/`TryGet<T>` are reference-type APIs; use the distinctly named unconstrained `GetValue<T>`/`TryGetValue<T>` for value types. A stored null is present for compatible reference types, while a missing key or type mismatch returns false from the `TryGet` method and default from `Get`.

An older bridge predating `inspect` rejects only that action with `runtime.action must be list, stop, or clear.` The host provides install/redeploy and game-restart guidance for this exact legacy error; existing `list`, `stop`, and `clear` actions still work.
